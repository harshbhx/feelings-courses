# How setup talks to Cloudflare (API behaviour, checked 23 Oct 2026)

`scripts/setup.mjs` uses Cloudflare's v4 API with the owner's token. This page records what each call does on Cloudflare's side, the hub's open questions, and where the answer comes from, so the script can be trusted before its first real run. It has still **not made a change on the real account**: run `--dry-run` first, then preview, then production.

`--dry-run` against the real account (DualMind Labs, 23 Oct 2026, placeholder Razorpay test keys) exited 0 and planned: create D1 `fbc-courses` and `fbc-courses-preview`, R2 `fbc-media` and `fbc-media-preview` (each with the 35-day backup rule), and the `fbc-courses-mailer` Worker; then `add` for the DB, MEDIA and MAILER bindings and all ten variables and secrets in both environments. The project's only other variable, `NODE_VERSION`, is kept. Nothing showed CHANGE or STOP.

| Question | Answer | Source | What setup does |
|---|---|---|---|
| **Does `PATCH /pages/projects/:name` merge or replace `env_vars`?** (the hub's open item) | **Merges per key.** A key set to `null` is deleted; keys left out are kept. Wrangler's own `wrangler pages secret put` sends a PATCH with only the one variable it sets (plus the project's `wrangler_config_hash`), and `secret delete` sends `{ NAME: null }`. Bindings (`d1_databases`, `r2_buckets`) follow the same per-key rule. | API reference, Pages → Projects → Edit: "To delete an environment variable, set its key to `null`"; wrangler 4.152.0 `pages secret` source | Sends only its own keys, echoes `wrangler_config_hash` when present, and still reads the project back afterwards: anything that existed before and is gone, or anything it set that is missing, is reported by name (never value). |
| Are secret values returned by `GET /pages/projects/:name`? | No usable value: secrets are write-only (dashboard: "You cannot see secrets after you set them"). | Pages Functions → Bindings → Secrets | Never compares secrets: the plan says "set again". The backup file stores secret **types** only. |
| Do new bindings apply at once? | Only to new deployments. | Pages Functions → Bindings: secrets "need to be done before a deployment that uses those secrets" | Tells the owner to **Retry deployment** afterwards. |
| A wrangler config in the repo? | When a Pages project has a wrangler config, its bindings come from the file at deploy time. | Pages Functions → Wrangler configuration | Refuses to run if `wrangler.toml` / `wrangler.json(c)` exists (the repo deliberately has none, `functions/_lib/env.ts`). |
| **Custom domain for a course subdomain** | Dashboard: Pages → Custom domains adds the CNAME by itself when the zone is on Cloudflare. API: `POST /accounts/:id/pages/projects/:name/domains` `{ name }` only attaches the domain (status `initializing` → `pending` → `active`); it does not create DNS. A CNAME made before the domain is attached gives a 522. Target: the project's `subdomain` (`<project>.pages.dev`), proxied. 100 custom domains per project on Free. | Pages → Custom domains; API reference, Pages → Domains → Create; Terraform/Pulumi `pages_domain` docs ("A DNS record for the domain is not automatically created"); Pages → Limits | `--add-domain <slug>`: attach first, then a proxied CNAME to `project.subdomain`; stops on any other record with that name; idempotent. Needs Zone Read + DNS Edit on the token; the owner guide keeps the dashboard way as the main one. |
| **Deploy hook creation** | Dashboard only (Settings → Builds → Add deploy hook). The URL works without authentication, so it is a secret. No API to create one is documented. | Pages → Deploy hooks | Takes the URL from `setup.local.json`, validates its shape, stores it as a secret on production only. |
| D1 create | `POST /accounts/:id/d1/database` `{ name, primary_location_hint }`; hints `wnam enam weur eeur apac oc`, only at creation. Response `uuid`. | API reference, D1 → Database → Create; D1 → Data location | Creates with `apac` (configurable as `cloudflare.location`), after the confirmation. |
| **D1 migrations apply** | `wrangler d1 migrations apply` needs the database in a wrangler config (with `migrations_dir`); this project has none on purpose. The site applies `migrations/*.sql` itself on the first request, each file as one atomic batch, recorded in wrangler's own `d1_migrations` table. The REST `query` endpoint is not used for migrations: it isn't documented to apply a multi-statement file atomically, and a half-applied file would block the runtime's own migration. | `functions/_lib/migrate.ts` | No migration step. The first visit after **Retry deployment** builds the schema; `go-live` treats "no such table" as "open the site once" instead of crashing. |
| D1 Time Travel bookmark | `GET /accounts/:id/d1/database/:id/time_travel/bookmark` returns the current `bookmark`. | API reference, D1 → Time Travel → Get bookmark | Saved in `setup.local.backup-<time>.json` before every change, for `wrangler d1 time-travel restore --bookmark`. |
| D1 free-plan limits | Since 1 Sep 2026 queries **fail** for the rest of the UTC day once an account passes 5 M rows read or 100 k rows written per day. | D1 changelog, 2026-09-01 | Documented in docs/owner/MONITORING.md. |
| R2 create | `POST /accounts/:id/r2/buckets` `{ name, locationHint }`. A missing bucket answers 404 (code 10006). An account without R2 answers code 10042 ("Please enable R2 through the Cloudflare Dashboard"). | API reference, R2 → Buckets → Create; R2 error codes | Creates with `apac` after the confirmation. 10042 becomes a plain instruction, before anything changed. |
| **R2 CORS** | Not needed. Uploads go through the site's own Functions (`PUT /api/admin/uploads/:id/parts/:n` on the same origin), and videos and images are served by Functions on the same host. A CORS rule would only matter for browser access to the bucket's S3 endpoint or a public bucket, which this design never uses. | docs/platform/MEDIA.md | No CORS rule. Checks the bucket is **not** public on r2.dev (`GET …/domains/managed`) and warns if it is. |
| **R2 lifecycle** | New buckets have a default rule aborting unfinished multipart uploads after 7 days. `PUT …/lifecycle` **replaces** all rules; `GET …/lifecycle` returns `{ rules }`. `maxAge` is in seconds. Objects go within about 24 h of expiry. Wrangler's `lifecycle add` reads, appends and writes back. | API reference, R2 → Buckets → Lifecycle → Update; R2 → Object lifecycles; wrangler source | Reads the rules, adds or fixes one rule (`fbc-backups-35d`: prefix `backups/d1/`, delete after 35 days, matching the privacy policy), writes back the full list with every other rule unchanged, and skips the write when nothing changes. The app's own pruning (last 35 dumps) stays. |

| **Mailer Worker upload** (email identity, 23 Oct 2026) | Pages Functions can't hold a `send_email` binding (Workers-vs-Pages table: Email Workers is Workers only), so a Worker holds it and Pages calls it through a **service binding** (`deployment_configs.<env>.services.MAILER = { service, environment }`, merged per key like the other bindings). Upload: `PUT /accounts/:id/workers/scripts/:name` as `multipart/form-data` with a `metadata` part (`main_module`, `compatibility_date`, `bindings`) and the module part (`application/javascript+module`); a `send_email` binding takes `allowed_sender_addresses`. `POST …/workers/scripts/:name/subdomain { enabled: false, previews_enabled: false }` turns `workers.dev` off. Sending to any address needs the domain onboarded in Email Sending and Workers Paid. | Workers → Multipart upload metadata; Email Service → Send bindings, Limits, Pricing; Pages → Bindings → Service bindings | Uploads `workers/mailer/index.js` (no build) with `EMAIL`, `EMAIL_FROM`, `EMAIL_FROM_NAME`, `MAILER_KEY`, turns the public URLs off, then binds `MAILER` on both environments. Re-uploads on every run (idempotent). Needs Workers Scripts: Edit. |

## What the script never does

- create a Pages project, a deploy hook, a token or anything in Razorpay;
- delete a resource, a variable or a binding (it never sends `null`);
- point an existing `DB` or `MEDIA` binding at a different database or bucket without `--allow-rebind`;
- put live keys on the preview environment (go-live is production only);
- print or save a secret anywhere but `setup.local.out.json` / `.out.txt` (mode 600, gitignored).

## Testing without Cloudflare

`tests/w7/setup.test.mjs` runs `main()` against a fake API that behaves as above (per-key merge, write-only secrets, replacing lifecycle PUT, the default multipart rule, 10042 without R2). It checks that a dry run and an unconfirmed run send no write, that a rerun only re-sends the PATCH, that hand-set variables survive, that nothing secret reaches the console or the backup file, the rebind guard, go-live's gates, and `--add-domain`'s order and conflict stop.
